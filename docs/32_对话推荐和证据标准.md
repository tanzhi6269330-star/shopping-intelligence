# 第32步：基于证据的商品推荐引擎

## 需求状态
品类、关键词、预算上限/大约预算/明确不限、用途、连接方式、商品状态（新品/二手）、省钱优先、指定品牌、排除品牌，以及游戏账号专属的游戏/区服。每轮输入只更新其命名的条件，切换品类时清理不适用的旧参数。

## 追问设计
最多先问最影响推荐的条件：①预算，②用途，③会显著影响选项的连接方式/游戏区服。用户不回答时仍可以打开研究搜索，不强行要求填写所有字段。说“便宜点”不猜新的预算上限，而是保留旧预算并询问新的价格上限。

## 来源与推荐准入
- 所有“型号研究候选”必须在代码中关联至少一个具体可访问的公开评测 URL；没有出处绝对不能进入候选池。
- 专业横评优先于营销型榜单。社区自述为线索，不代表独立测量；缺少独立交叉验证必须标记来源单薄。
- 当前资料相关性分由来源类别、来源数量、用途匹配及连接方式相容性确定，**不是性能分、购买价值分或实时折扣分**。
- 页面显示的历史文章提及价不是任何时刻的到手价；不展示“今日最低”“已验真”“全平台第一”之类无依据的结论。
- 盼之代售的游戏账号不能与普通商品混排，实名、换绑、找回保障等必须单独验号；闲鱼核成色/卖家；1688核最低起订量/阶梯价。
- 只有真实价格、指定 SKU、优惠、运费和附加费得到完整核验后，才允许标记“购买候选”；目前聊天版暂不具备此阶段能力。

## 数据流
自由聊天 → 轻量规则状态识别 → 信息价值最高的追问 → 研究候选与来源 → 用户确认偏好 → 外部专业评测/社区搜索和电商搜索 → 后续真实商品价格验证。

## 目前真实覆盖
仅耳机类建立少量具体型号研究线索；其他品类仅提供对话收敛和有针对性的检索入口，明确“不足以推荐具体型号”。不采用占位商品、虚构优惠或演示产品假装真实商品。

## 下一步判定
要实现真正的自动跨平台采购助手，必须有可用的搜索 API/合规授权数据访问与模型推理后端，部署成本、限制及数据准确率需分别实测。GitHub Pages 是静态托管，不会因为对话界面存在就具有联网 AI 搜索能力。
